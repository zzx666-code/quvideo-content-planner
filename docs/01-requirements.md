# 需求与成功标准

## 用户与目标

运营人员希望在给定预算和截止时间内得到一份可执行的内容活动方案。输入为主题、预算、截止时间及可选的制作档位偏好；材料为带来源 ID 的合成素材、费用和耗时表。

活动方案必须包含：任务与依赖、步骤状态、实际工具结果、费用合计、制作耗时、稿件和素材引用，以及已保存方案或未完成原因。

## 范围与假设

1. 单机 CLI、单 Agent，基于 pi。工具均为本地函数，素材及产品事实全部为合成资料。
2. 预算约束最终拟议活动方案的成本，估算不代表已经发生支出；模拟工具不实际扣费。模型 API 的实际花费不计入活动预算，单独记录 token，未配置单价时费用为未知。
3. 耗时表描述预计内容制作时间，按依赖顺序相加；与程序执行耗时分别记录。保存后的制作任务仍为 `planned`。
4. 档位偏好是软约束；预算和截止时间是硬约束。模型可以降低制作档位，不能擅自增加预算或推迟截止时间。
5. 不以命中某个固定用例作为成功依据。费用表变化、工具错误变化后，模型须根据新返回结果调整动作。

## 验收映射

| 题面要求 | 验收方式 |
| --- | --- |
| 正常完成 | 完成四工具链路，保存文件与输出的费用、稿件和 ID 一致 |
| 缺预算或截止时间 | 分开测试两项，返回 `needs_input`，无模型调用、不保存 |
| 工具失败 | 注入一次脚本错误，模型可调整或有限重试；保留成功检索结果 |
| 预算超限 | 预算 10，初稿估算 12；模型改选可行方案，再估算和保存 |
| 无可行方案 | 返回 `incomplete`，列出表内最低预算、最短耗时和缺口 |
| 重复执行 | 同请求复用结果，本次调用计数 0，一份方案；不同输入复用 ID 返回冲突 |
| 失败步骤续跑（加分） | 显式 `--resume`，复用素材、稿件和有效估算，保存前仍重新检查约束 |
| 真实动态决策循环 | 真实模型完成至少两条不同路径，Trace 记录参数、工具返回和后续动作依据 |
| 执行上限 | 模型轮数、工具调用、墙钟超时分别验证，触顶明确未完成 |
| 交付规范 | CLI、可执行测试、实际运行记录、五份文档、锁定依赖、环境示例、AI 使用说明 |

## 完成定义

只有 `save_plan` 工具确认方案实际写入文件，任务才是 `completed`。模型文本声称成功、某个步骤成功或预估满足条件，均不能替代保存回执。方案变化必须对应新的估算；保存前再次检查截止时间和预算。
